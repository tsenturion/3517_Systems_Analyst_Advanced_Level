## Подсказки по ключевым частям

### Как связать правило с ограничением

| Правило | Как отразить в схеме |
| --- | --- |
| У каждой строки есть свой идентификатор | `PRIMARY KEY` |
| Поле обязательно | `NOT NULL` |
| Связанный объект должен существовать | Внешний ключ |
| Одна комбинация значений может встретиться один раз | `UNIQUE` для нужного поля или группы полей |
| Значения в одной строке должны удовлетворять условию | `CHECK`, например `CHECK (ends_at > starts_at)` |

При проверке интервала `CHECK` отклонит запись, где конец раньше начала или совпадает с ним. Чтобы отклонить запись с отсутствующей границей интервала, задайте `NOT NULL` на обоих полях. По той же причине обязательную ссылку на объект дополняют `NOT NULL`. [Поведение ограничений при `NULL` в PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html).

### Как выглядит рабочий SQL на примере выдачи оборудования

В примере у заявки один предмет оборудования и обязательный интервал выдачи. Запустите блок целиком, чтобы увидеть одну строку с заявкой `101` и оборудованием `INV-014`. Затем используйте структуру примера для своего сценария.

```sql
CREATE TEMP TABLE practice10_equipment (
    id integer PRIMARY KEY,
    inventory_number text NOT NULL UNIQUE,
    name text NOT NULL
);

CREATE TEMP TABLE practice10_issue_requests (
    id integer PRIMARY KEY,
    equipment_id integer NOT NULL,
    starts_at timestamptz NOT NULL,
    ends_at timestamptz NOT NULL,
    CONSTRAINT issue_request_equipment_fk
        FOREIGN KEY (equipment_id) REFERENCES practice10_equipment (id),
    CONSTRAINT issue_request_interval_check CHECK (ends_at > starts_at)
);

INSERT INTO practice10_equipment (id, inventory_number, name)
VALUES (1, 'INV-014', 'Проектор');

INSERT INTO practice10_issue_requests (id, equipment_id, starts_at, ends_at)
VALUES (101, 1, '2026-10-06 10:00:00+05:00', '2026-10-06 11:00:00+05:00');

SELECT r.id AS request_id, e.inventory_number, e.name, r.starts_at, r.ends_at
FROM practice10_issue_requests AS r
JOIN practice10_equipment AS e ON e.id = r.equipment_id
WHERE e.inventory_number = 'INV-014'
ORDER BY r.starts_at, r.id;
```

Первая ошибочная вставка указывает оборудование `999`, которого нет в таблице. PostgreSQL должен сообщить о нарушении `issue_request_equipment_fk`.

```sql
INSERT INTO practice10_issue_requests (id, equipment_id, starts_at, ends_at)
VALUES (102, 999, '2026-10-06 10:00:00+05:00', '2026-10-06 11:00:00+05:00');
```

Вторая вставка ссылается на существующее оборудование, но конец интервала раньше начала. Ожидается нарушение `issue_request_interval_check`.

```sql
INSERT INTO practice10_issue_requests (id, equipment_id, starts_at, ends_at)
VALUES (103, 1, '2026-10-06 11:00:00+05:00', '2026-10-06 10:00:00+05:00');
```

### Как представить ту же запись документом

Например, в документе заявки `101` можно хранить снимок сведений об оборудовании на момент подачи. Тогда карточка заявки показывает прежнее название, даже если оно позже изменится в справочнике.

```json
{
  "requestId": 101,
  "equipment": {
    "id": 1,
    "inventoryNumber": "INV-014",
    "name": "Проектор"
  },
  "startsAt": "2026-10-06T10:00:00+05:00",
  "endsAt": "2026-10-06T11:00:00+05:00"
}
```

Если карточка всегда должна показывать актуальное название, рассмотрите ссылку `equipmentId` и хранение названия в справочнике. В выводе объясните, что выбрали для своей операции и как этот выбор влияет на чтение и обновление данных. [Вложенные документы и ссылки в MongoDB](https://www.mongodb.com/docs/manual/data-modeling/best-practices/).
