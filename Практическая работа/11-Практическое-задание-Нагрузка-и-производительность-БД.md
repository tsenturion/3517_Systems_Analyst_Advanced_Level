# Практическое задание «Оценка нагрузки и проверка индекса в PostgreSQL»

**Темы курса** — 6.3 «Способы прогнозирования нагрузки на приложения. Способы повышения производительности БД» и 6.4 «Доработка архитектуры приложения с учётом предполагаемой нагрузки».

Практика для самостоятельного закрепления навыков. Сдача по желанию.

## Цель

Оценить, сколько обращений к базе создаёт одна операция в пиковый период. Сравнить планы одного SQL-запроса до и после добавления индекса. На основе расчёта и замеров предложить изменение в проекте или следующую проверку.

## Задание

Для сравнения до и после индекса можно выделить из него часть, отвечающую за отбор строк. Запишите, какие условия и поля вы перенесли. [Задание № 10 «Проектирование хранения данных»](./10-Практическое-задание-Проектирование-хранения-данных.md).

Для «Севера» перенесите отбор по аудитории из запроса списка заявок и добавьте отбор по дню начала интервала. Возьмите поля заявки из схемы № 10. В учебном замере достаточно части запроса, которая читает время и статус заявки из одной таблицы. Для своего сценария аналогично выберите фильтр по объекту и диапазону времени. Запишите, кто вызывает операцию, что она возвращает и с какими параметрами будете выполнять замер.

### Шаг 2. Оцените нагрузку в самый загруженный период

1. Выберите интервал, в котором ожидаете всплеск, и запишите его длительность в секундах. Например, после открытия расписания администраторы нескольких площадок одновременно проверяют заявки.
2. Оцените количество вызовов операции за этот интервал. Если исходная цифра — число пользователей, умножьте её на среднее число вызовов на пользователя. Если есть журнал с числом вызовов, используйте его напрямую. Для каждого числа отметьте, взято ли оно из данных или принято как допущение.
3. Разделите число вызовов на длительность интервала. Получится средняя интенсивность операции за выбранное окно в запросах в секунду (RPS). Если операция вызывает несколько SQL-запросов, умножьте интенсивность на это число, чтобы оценить обращения к базе в секунду.
4. Если трафик в пределах выбранного интервала распределён неравномерно, отдельно посчитайте более короткое окно. Запишите, какую оценку возьмёте для следующей проверки и на каком допущении она держится.

**Пример для «Севера».** Допустим, в первую минуту 240 администраторов открывают список в среднем по два раза. Получаем `240 × 2 / 60 = 8` вызовов в секунду за минуту. Из этих 480 вызовов 180 приходятся на самые загруженные 10 секунд. Тогда за короткое окно получается `180 / 10 = 18` вызовов в секунду. Если на каждый вызов приходится один `SELECT`, ориентир для проверки — около 18 SQL-запросов в секунду за это окно.

### Шаг 4. Получите план до добавления индекса

Сначала выполните обычный `SELECT` и проверьте результат. В примере ниже он вернёт 24 заявки по аудитории `42` за 6 октября 2026 года по времени UTC+5. Верхняя граница открытая. Заявка, начинающаяся ровно в полночь 7 октября, попадёт в выборку за следующий день.

```sql
SELECT request_id, starts_at, ends_at, status
FROM practice11_requests
WHERE room_id = 42
  AND starts_at >= TIMESTAMPTZ '2026-10-06 00:00:00+05:00'
  AND starts_at <  TIMESTAMPTZ '2026-10-07 00:00:00+05:00'
ORDER BY starts_at;
```

Добавьте строку `EXPLAIN (ANALYZE, BUFFERS)` перед `SELECT` и выполните запрос вместе с ней. PostgreSQL выполнит запрос и вернёт его план. Сохраните текст плана. Запишите способ чтения таблицы, фактическое число строк из верхнего узла и `Execution Time` в миллисекундах. [Чтение планов выполнения в PostgreSQL](https://www.postgresql.org/docs/current/using-explain.html).

## Учебные данные

Таблица содержит по 500 заявок на каждую из 200 аудиторий. В каждой аудитории начало интервала сдвигается на час, а продолжительность интервала составляет 30 минут.

```sql
CREATE TEMP TABLE practice11_requests (
    request_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_id integer NOT NULL,
    starts_at timestamptz NOT NULL,
    ends_at timestamptz NOT NULL,
    status text NOT NULL,
    CHECK (ends_at > starts_at)
);

INSERT INTO practice11_requests (room_id, starts_at, ends_at, status)
SELECT room.id,
       TIMESTAMPTZ '2026-10-01 00:00:00+05:00' + slot.n * INTERVAL '1 hour',
       TIMESTAMPTZ '2026-10-01 00:30:00+05:00' + slot.n * INTERVAL '1 hour',
       CASE slot.n % 3
           WHEN 0 THEN 'APPROVED'
           WHEN 1 THEN 'PENDING'
           ELSE 'REJECTED'
       END
FROM generate_series(1, 200) AS room(id)
CROSS JOIN generate_series(0, 499) AS slot(n);

ANALYZE practice11_requests;

SELECT count(*) AS request_count
FROM practice11_requests;
```

Каждая строка из первого `generate_series` соединяется с каждой строкой из второго. Поэтому получается `200 × 500` записей. [Генерация рядов в PostgreSQL](https://www.postgresql.org/docs/current/functions-srf.html).

## Подсказки по ключевым частям

- `Seq Scan` обозначает последовательный просмотр таблицы. Строка `Rows Removed by Filter` показывает, сколько строк узел отбросил по условию.
- Ищите в плане `Index Scan` или `Bitmap Index Scan` и имя индекса. `Index Cond` показывает условия, по которым PostgreSQL ищет подходящие ключи. Если в плане есть узел `Sort`, проверьте, присутствует ли он в обоих вариантах.
- `rows` рядом с `cost` — оценка планировщика. Для фактического результата смотрите `rows` в части `actual`. В этом примере верхний узел обычно выполняется один раз (`loops=1`).
- У временной таблицы данные в плане отражаются в `Buffers: local`. `hit` означает, что нужный блок уже был в буфере PostgreSQL, а `read` — что его пришлось загрузить в буфер. Показатели верхнего узла уже учитывают дочерние узлы. [Статистика буферов в EXPLAIN](https://www.postgresql.org/docs/current/sql-explain.html).
- `Execution Time` описывает один запуск SQL в базе. Для проверки заданного RPS понадобится отдельный замер с одновременными вызовами операции. Время ответа интерфейса или API измеряйте на соответствующем уровне.

## Советы по улучшению работы

- Сделайте по несколько запусков до и после создания индекса. Запишите, какой запуск сравниваете и насколько отличаются времена. Повторное выполнение может использовать уже загруженные блоки.
- Во втором эксперименте расширьте диапазон дат или возьмите операцию без фильтра по аудитории. Сравните, как меняется план, когда запросу нужна большая доля таблицы.
- Перед решением о добавлении индекса в рабочую схему учтите операции записи. Индекс занимает место, а при изменении индексируемых данных PostgreSQL обновляет его. Если запись важна для сценария, предложите замерить чтение и запись в одном тесте. [Стоимость сопровождения индексов в PostgreSQL](https://www.postgresql.org/docs/current/indexes-intro.html).
