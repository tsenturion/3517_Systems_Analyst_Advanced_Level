# Практическое задание «Проектирование REST API»

**Темы курса** — 4.1 «Принципы работы API. RESTful API и SOAP» и 4.2 «Проектирование структуры API собственного приложения, исследование внешних API, подготовка сценариев работы, документирование API».

Практика для самостоятельного закрепления навыков. Сдача по желанию.

## Цель

Спроектировать 2–3 операции API для одного сценария. Определить, кто вызывает каждую операцию, какие данные отправляет клиент и какой ответ возвращает сервер при успехе и ошибке.

## Задание

### Шаг 1. Выберите сценарий и действия клиента

Возьмите одну операцию из своего проекта. Запишите, кто пользуется системой, какие действия выполняет и какие правила влияют на результат. Для выбора данных можно опираться на информационную модель, а для определения границы приложения — на схему компонентов. [Задание № 4 «Проектирование информационной модели»](./04-Практическое-задание-Информационная-модель.md) · [Задание № 5 «Архитектура и интеграции»](./05-Практическое-задание-Архитектура-и-интеграции.md).

**Условия для самостоятельного старта.** Возьмите сервис бронирования аудиторий учебного центра «Север». Координатор подаёт разовую заявку на аудиторию и может посмотреть её статус. В заявке указываются аудитория, начало и конец нужного интервала. После подачи заявка имеет статус «На рассмотрении» и сама по себе не занимает интервал. Администратор может подтвердить заявку, если интервал не пересекается с подтверждённой бронью или служебным закрытием той же аудитории. Детали заявки доступны её автору и администраторам. [Исходный кейс задания № 3](./03-2.12-Практическое-задание-Управление-изменениями-и-трассировка.md).

Для первой попытки спроектируйте подачу заявки и просмотр её статуса. Третьей операцией можно добавить подтверждение заявки администратором. Для своего кейса выберите похожую последовательность, в которой клиент создаёт или изменяет данные и затем получает результат.

### Шаг 2. Посмотрите одну операцию внешнего API

Откройте описание **Get an issue** в GitHub REST API. Найдите метод и путь, выпишите обязательные параметры пути и один код успешного ответа. Затем найдите код, который возвращается, когда ресурс не найден. Достаточно прочитать документацию. [GitHub REST API — Get an issue](https://docs.github.com/en/rest/issues/issues#get-an-issue).

Сохраните короткую запись с методом, путём и кодами. Используйте её как образец того, как отделить входные данные операции от её результатов.

### Шаг 3. Назовите ресурсы и выберите методы

**Ресурс** — то, с чем клиент работает через API, например заявка. **Коллекция** — набор ресурсов одного вида, например список заявок. **Операция** определяется парой «HTTP-метод и путь». Сначала запишите ресурс и его идентификатор, затем сопоставьте операции с действиями пользователя.

| Действие клиента | Как оформить |
| --- | --- |
| Получить сведения об одной записи | Используйте `GET` с идентификатором в пути. Например, `GET /equipment-requests/{requestId}`. |
| Создать запись в коллекции | Используйте `POST` к пути коллекции. Например, `POST /equipment-requests`. |
| Изменить часть существующей записи | Рассмотрите `PATCH` с идентификатором в пути. Укажите, какие поля можно менять и в каком формате клиент передаёт изменения. |

Для подтверждения заявки можно, например, создать связанное решение отдельной операцией `POST` или описать разрешённое изменение состояния через `PATCH`. Выберите один вариант и поясните, с каким ресурсом работает клиент. [Методы GET и POST в RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3) · [Метод PATCH в RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html#section-2).

### Шаг 4. Заполните таблицу операций

Сделайте по одной строке для каждой из 2–3 операций. Запишите, кто её вызывает, какие данные нужны, что вернётся при успехе и в какой ситуации возможна ошибка.

| Действие и роль | Метод и путь | Входные данные | Успешный ответ | Ошибка и условие |
| --- | --- | --- | --- | --- |
| Получить заявку на выдачу оборудования. Вызывает автор заявки. | `GET /equipment-requests/{requestId}` | `requestId` — обязательная строка в пути | `200` и данные заявки со статусом | `404`, если заявки с таким идентификатором нет |

Для каждого поля укажите тип и обязательность. Идентификатор конкретного ресурса обычно берут из пути. Параметры после `?` подходят для фильтрации или других настроек чтения, если они нужны вашему сценарию. Данные для создания записи передаются в теле запроса. Состав ответа определите исходя из того, что клиенту нужно для следующего действия.

### Шаг 5. Подготовьте примеры запроса и ответов

Выберите одну операцию, которая создаёт или изменяет данные. Для неё запишите метод и путь с конкретными значениями параметров, тело запроса в JSON, код и тело успешного ответа. Затем подготовьте ошибочный запрос или укажите состояние, в котором операция завершится ошибкой. Покажите, какой код и сообщение получит клиент.

Привяжите ошибку к конкретному условию. Например, если обязательное поле отсутствует, клиенту нужно добавить его. Если подтверждение заявки конфликтует с уже существующей бронью, клиенту нужно получить актуальные сведения об интервале или выбрать другой. Для ошибки запишите, что произошло с данными.

### Шаг 6. Пройдите по сценарию и соберите результат

1. Проследите успешный ход от первой операции до последней. Проверьте, что идентификатор из ответа на создание можно использовать в запросе на чтение. Если есть операция подтверждения, проследите, как клиент узнает итоговый статус.
2. Пройдите по одному ошибочному ходу. Запишите, какая операция завершилась ошибкой, изменились ли данные и что клиент может сделать дальше.
3. Сохраните в одном Markdown-файле границы сценария, короткий разбор внешней операции, таблицу своих операций и примеры JSON. Этот документ пригодится для описания контракта в OpenAPI в следующем задании.

## Подсказки по ключевым частям

- **REST и SOAP.** В этой работе используется REST API поверх HTTP. Путь указывает на ресурс, а метод передаёт смысл операции. SOAP задаёт собственную структуру сообщения на основе XML. [Семантика HTTP](https://www.rfc-editor.org/rfc/rfc9110.html#section-9) · [Спецификация SOAP 1.2](https://www.w3.org/TR/soap12-part1/).
- **Успех и ошибка.** `200 OK` подходит для успешного чтения, `201 Created` — для ответа о созданном ресурсе. `400 Bad Request` может обозначать ошибку во входных данных, `403 Forbidden` — отказ в доступе, `404 Not Found` — отсутствие ресурса, а `409 Conflict` — конфликт с его текущим состоянием. Выберите коды, которые соответствуют условиям вашего API. [Коды ответа HTTP](https://www.rfc-editor.org/rfc/rfc9110.html#section-15).
- **Два вида статусов.** HTTP-код описывает результат запроса, а поле `status` внутри JSON — состояние заявки. Созданная заявка может вернуться с кодом `201` и при этом иметь состояние «На рассмотрении». [Описание ответа 201 Created](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.2).
- **Доступ.** Для каждой операции укажите роль и область доступа. Например, автор читает свою заявку, а администратор работает с заявками своей площадки, если это предусмотрено правилами выбранного кейса.

### Пример для сервиса выдачи оборудования

Сотрудник создаёт заявку на оборудование, а затем может получить её по идентификатору. Сервер назначает номер заявки и начальный статус.

**Запрос `POST /equipment-requests`.** Поля `equipmentId` и `requestedFor` — обязательные строки. Первое содержит идентификатор оборудования, второе — дату выдачи в формате год-месяц-день.

```json
{
  "equipmentId": "EQ-17",
  "requestedFor": "2026-11-16"
}
```

**Успешный ответ `201 Created`.** Заголовок `Location` указывает на `/equipment-requests/REQ-101`.

```json
{
  "requestId": "REQ-101",
  "equipmentId": "EQ-17",
  "requestedFor": "2026-11-16",
  "status": "PENDING"
}
```

Клиент может вызвать `GET /equipment-requests/REQ-101` и получить актуальные данные заявки с кодом `200 OK`.

**Ошибочный запрос `POST /equipment-requests`.** Клиент передал идентификатор оборудования и пропустил поле `requestedFor`.

```json
{
  "equipmentId": "EQ-17"
}
```

**Ответ `400 Bad Request`.** Операция завершилась на проверке входных данных до создания заявки.

```json
{
  "code": "REQUIRED_FIELD_MISSING",
  "message": "Укажите дату выдачи",
  "field": "requestedFor"
}
```

## Что проверить перед отправкой

Используйте чек-лист для самопроверки или перед отправкой, если решите поделиться результатом.

- [ ] Выбран один сценарий, записаны 2–3 операции и короткий разбор внешнего API.
- [ ] У каждой операции есть назначение, роль, HTTP-метод и путь.
- [ ] Указаны место передачи, тип и обязательность входных данных.
- [ ] Для каждой операции указан успешный ответ и хотя бы одна ошибка с условием её возникновения.
- [ ] JSON-примеры используют те же имена полей, идентификаторы и статусы, что и таблица.
- [ ] По описанию можно пройти успешный и ошибочный ход и понять, что изменится в системе.

## Советы по улучшению работы

- Прочитайте операции в том порядке, в котором их вызывает клиент. Убедитесь, что для следующего вызова уже известны нужные данные.
- Возьмите два разных случая, например пропущенное поле и изменение состояния между двумя запросами. Проверьте, помогает ли каждый ответ клиенту понять, что делать дальше.
- Сверьте названия и типы полей во всех примерах. Если идентификатор в ответе строковый, примеры чтения и изменения должны использовать тот же формат.
