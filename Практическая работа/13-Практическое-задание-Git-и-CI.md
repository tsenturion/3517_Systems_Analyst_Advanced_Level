# Практическое задание «Работа с Git и автоматическая проверка OpenAPI»

**Темы курса** — 7.2 «Системы контроля версий. GitFlow. Автоматическая доставка кода. CI/CD» и 7.3 «Работа с репозиториями».

Практика для самостоятельного закрепления навыков. Сдача по желанию.

## Цель

Внести небольшое изменение в контракт API в отдельной ветке Git и оформить запрос на слияние. Настроить проверку OpenAPI в GitHub Actions, найти причину сбоя по журналу и подтвердить исправление повторным запуском.

## Задание

### Шаг 1. Создайте учебный репозиторий и откройте его локально

1. Убедитесь, что команда `git --version` выводит номер версии. На GitHub создайте отдельный репозиторий `openapi-ci-practice`, выберите **Private** и добавьте `README.md` при создании. Репозиторий должен быть доступен вам на запись, а во вкладке **Actions** должен быть доступен запуск рабочих процессов. [Создание репозитория на GitHub](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-new-repository) · [Начало работы с GitHub Actions](https://docs.github.com/en/actions/get-started/quickstart).
2. На странице репозитория откройте **Code → HTTPS** и скопируйте адрес. В терминале перейдите в папку, где хотите хранить проект. Подставьте свой адрес вместо примера и выполните команды. При запросе авторизации воспользуйтесь входом в GitHub через Git Credential Manager или уже настроенным способом доступа. [Клонирование репозитория](https://docs.github.com/en/repositories/creating-and-managing-repositories/cloning-a-repository) · [Хранение учётных данных Git](https://docs.github.com/en/get-started/git-basics/caching-your-github-credentials-in-git).

```bash
git clone https://github.com/ВАШ-ЛОГИН/openapi-ci-practice.git
cd openapi-ci-practice
git branch --show-current
```

3. Запишите имя текущей ветки. В примере дальше она называется `main`. В эту ветку попадут исходный контракт и настройка проверки. Для изменения контракта создадите отдельную ветку.

### Шаг 2. Положите исходный контракт и настройте проверку

1. Положите в корень репозитория `openapi.yaml` итогового проекта из задания № 7. Для этой практики используйте один файл с внутренними ссылками `$ref` вида `#/components/…`. Для рабочего сценария подготовьте учебную копию своего контракта с вымышленными адресами и данными. [Задание № 7 «Контракт OpenAPI и взаимодействие фронтенда с бэкендом»](./07-Практическое-задание-OpenAPI.md).
2. Создайте в корне каталог `.github`, в нём каталог `workflows`, а в нём файл `openapi.yml`. Скопируйте содержимое ниже. Если исходная ветка называется иначе, подставьте её имя вместо `main` в разделе `push`. [Синтаксис рабочих процессов GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).

```yaml
name: Проверка OpenAPI

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  lint:
    name: Валидация контракта
    runs-on: ubuntu-latest
    steps:
      - name: Получить файлы репозитория
        uses: actions/checkout@v6
      - name: Подготовить Node.js
        uses: actions/setup-node@v6
        with:
          node-version: '22'
      - name: Проверить openapi.yaml
        run: npx --yes @redocly/cli@2.64.1 lint --extends=spec openapi.yaml
```

Рабочий процесс запускается при отправке коммита в основную ветку и при открытии или обновлении pull request. Redocly CLI проверяет `openapi.yaml` набором правил `spec`. [События запуска GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request) · [Команда Redocly lint](https://redocly.com/docs/cli/commands/lint).

3. Сохраните оба файла в исходной ветке и отправьте их в свой репозиторий.

```bash
git add openapi.yaml .github/workflows/openapi.yml
git commit -m "Добавить контракт и проверку OpenAPI"
git push
```

Если Git просит указать имя автора или email, задайте `user.name` и `user.email` командой `git config --local` в учебном репозитории и повторите коммит. [Настройка имени пользователя Git](https://docs.github.com/en/get-started/git-basics/setting-your-username-in-git) · [Настройка адреса для коммитов](https://docs.github.com/en/account-and-profile/how-tos/email-preferences/setting-your-commit-email-address).

4. Откройте **Actions → Проверка OpenAPI**, выберите запуск и раскройте шаг **Проверить openapi.yaml**. Убедитесь, что он завершился успешно. Если проверка выявила проблему в исходном контракте, исправьте её в основной ветке и дождитесь успешного запуска перед следующим шагом.

### Шаг 3. Внесите изменение в отдельной ветке

1. Создайте рабочую ветку от исходной. Проверьте её имя.

```bash
git switch -c docs/openapi-summary
git branch --show-current
```

2. Выберите одну операцию проекта и уточните её `summary`. Например, в «Севере» у `POST /booking-requests/{requestId}/bookings` можно уточнить, что операция подтверждает разовую заявку и создаёт бронь. Опирайтесь на действие и результат, описанные в задании № 6 или № 12. Запишите, какую операцию изменили и зачем.
3. В том же файле временно удалите строку `version` внутри блока `info`. Запомните её исходное значение для восстановления. Поле `info.version` обязательно, поэтому проверка должна завершиться ошибкой. Строка `openapi: 3.0.3` в корне файла задаёт версию спецификации и остаётся в файле. [Поля объекта Info в OpenAPI 3.0.3](https://spec.openapis.org/oas/v3.0.3#info-object).
4. Проверьте, что в `git diff` видны уточнение `summary` и удаление `info.version`. Затем создайте коммит и отправьте рабочую ветку.

```bash
git diff -- openapi.yaml
git add openapi.yaml
git commit -m "Уточнить описание операции и проверить реакцию CI"
git push -u origin docs/openapi-summary
```

### Шаг 4. Откройте pull request и прочитайте ошибку

1. В репозитории на GitHub откройте **Pull requests → New pull request**. В поле **base** выберите исходную ветку, в поле **compare** — `docs/openapi-summary`. Нажмите **Create pull request**. [Создание pull request на GitHub](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request).
2. Дайте pull request заголовок, который описывает полезное изменение, например «Уточнить описание операции получения заявки». В описании укажите, что и зачем меняете, как это проверить и какое поле временно удалили для проверки CI.
3. Дождитесь результата **Валидация контракта** во вкладке **Checks**. Откройте журнал шага **Проверить openapi.yaml**. Redocly укажет путь `#/info` и сообщение «The field `version` must be present on this level». Сохраните сообщение или ссылку на запуск. Если сбой произошёл на подготовке среды или установке инструмента, сначала устраните эту причину и дождитесь запуска проверки контракта. [Просмотр журналов GitHub Actions](https://docs.github.com/en/actions/monitoring-and-troubleshooting-workflows/monitoring-workflows/using-workflow-run-logs).

### Шаг 5. Исправьте контракт и проверьте итог pull request

1. В той же рабочей ветке верните строку `version` в раздел `info` с исходным значением и отступом. Уточнённое `summary` сохраните. Отправьте исправление отдельным коммитом.

```bash
git diff -- openapi.yaml
git add openapi.yaml
git commit -m "Восстановить версию API в контракте"
git push
```

2. Откройте тот же pull request. GitHub запустит проверку на новом коммите. Убедитесь, что **Валидация контракта** прошла, и сохраните результат. На вкладке **Files changed** проверьте, что итоговый diff относительно основной ветки содержит только полезное изменение.
3. Обновите описание pull request. Запишите причину первой ошибки и результат повторного запуска. Для завершения задания достаточно открытого pull request с успешной проверкой.

### Шаг 6. Соберите результат

Добавьте к материалам итогового проекта проверенную версию `openapi.yaml`, файл рабочего процесса и адрес pull request. В короткой записи укажите название ветки, изменение в контракте, сообщение первой проверки и результат второй. Эту версию контракта возьмите для тестирования в задании № 14. Если будете делиться результатом из закрытого репозитория, приложите выдержки из журналов и итоговый diff.

## Подсказки по ключевым частям

- **Ветка и pull request.** Ветка хранит серию коммитов. Pull request показывает, какие изменения эта ветка предлагает внести в базовую. Новый коммит в исходной ветке pull request обновляет тот же запрос на слияние.
- **Связь с GitFlow.** В упражнении рабочая ветка создаётся от `main`. В классическом GitFlow ветки для функциональных изменений создаются от `develop` и возвращаются в неё. В обоих случаях сначала определите, откуда взять исходный код и в какую ветку должно попасть изменение. [Описание модели GitFlow](https://nvie.com/posts/a-successful-git-branching-model/).
- **Граница проверки.** В этой практике настроена непрерывная интеграция (CI). GitHub Actions запускает проверку файла при изменении. Валидация OpenAPI проверяет структуру описания, а поведение работающего API проверяется отдельными запросами.
- **Файлы не видны в Actions.** Сверьте точный путь `.github/workflows/openapi.yml` и расширение файла. Проверьте во вкладке **Code**, что `openapi.yaml` лежит в корне репозитория и оба файла попали в отправленный коммит.
- **Локальный запуск.** Для той же проверки в терминале установите Node.js 22 версии 22.12 или новее в линейке 22 и откройте корень проекта. В Windows PowerShell используйте `npx.cmd`. Если GitHub Actions недоступен, локально можно отработать поиск и исправление ошибки, сохранив вывод двух запусков.

```powershell
npx.cmd --yes @redocly/cli@2.64.1 lint --extends=spec openapi.yaml
```

В macOS или Linux используйте `npx` с теми же аргументами.

## Что проверить перед отправкой

- [ ] Исходный контракт и файл рабочего процесса находятся в основной ветке, исходная проверка прошла.
- [ ] Изменение контракта выполнено в отдельной ветке. В pull request выбраны правильные базовая и рабочая ветки.
- [ ] Сохранено сообщение, из которого видно, что первый запуск завершился ошибкой из-за отсутствия `info.version`.
- [ ] После исправления новый запуск в том же pull request прошёл успешно.
- [ ] Итоговый diff содержит полезное изменение, а описание pull request объясняет, зачем оно сделано и как проверено.

## Советы по улучшению работы

- Запускайте локальную проверку перед обычным коммитом, чтобы увидеть проблему до отправки в репозиторий.
- Сравните вкладки **Commits** и **Files changed**. В первой видны промежуточные коммиты, во второй — итоговое изменение относительно базовой ветки.
- В описании pull request явно укажите, что доказала проверка. Например, после исправления описание соответствует правилам структуры OpenAPI, а корректность ответа API можно проверить в следующем задании.

## Вопросы для рефлексии

1. Что даёт отдельная ветка, когда изменение ещё не прошло проверку?
2. Где в журнале вы нашли причину сбоя и как отличили её от ошибки установки инструмента?
3. Почему удаление и восстановление `info.version` видны в истории коммитов, а в итоговом diff этой правки нет?
4. Какую ошибку в поведении API можно пропустить даже при успешной проверке OpenAPI?
5. Какую проверку вы бы добавили, если бы потребовалось убедиться, что новый контракт сохраняет совместимость с существующими клиентами?
