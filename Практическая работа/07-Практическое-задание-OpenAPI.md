# Практическое задание «Контракт OpenAPI и взаимодействие фронтенда с бэкендом»

**Темы курса** — 4.3 «Проектирование ресурсной модели OpenAPI» и 4.4 «Взаимодействие фронтенда и бэкенда через API».

Практика для самостоятельного закрепления навыков. Сдача по желанию.

## Цель

Перенести описание 2–3 REST-операций в файл OpenAPI, проверить его и связать операции с действиями пользователя. По результату должно быть понятно, какой запрос отправляет интерфейс и что он показывает при успешном ответе и при ошибке.

## Задание

### Шаг 1. Возьмите операции из предыдущего задания

Откройте таблицу операций итогового проекта из задания № 6. Выпишите метод, путь, входные поля, успешный ответ и ошибки для каждой операции выбранного сценария. [Задание № 6 «Проектирование REST API»](./06-Практическое-задание-Проектирование-REST-API.md).

Для кейса «Север» перенесите операции открытия заявки, подтверждения и чтения созданной брони. В ответе `201` опишите `Location` в разделе `headers` и приведите пример пути к созданной брони. В ответе `409` укажите условия отказа и соответствующие коды ошибок из задания № 6. Пример с выдачей оборудования ниже показывает структуру YAML для переноса операций вашего проекта.

### Шаг 2. Создайте файл OpenAPI

Создайте текстовый файл `openapi.yaml`. Используйте в нём OpenAPI 3.0.3 и начните с трёх разделов.

| Раздел | Что записать |
| --- | --- |
| `openapi` | Версия формата описания. Для этой работы используйте `3.0.3`. |
| `info` | Название API в `title` и версия самого API в `version`, например `1.0.0`. |
| `paths` | Пути ресурсов. Под каждым путём перечислите методы, например `post` или `get`. |

Возьмите пример из подсказок как основу. Для своей работы замените пути и данные на те, которые выбрали в шаге 1. [Структура документа OpenAPI 3.0.3](https://spec.openapis.org/oas/v3.0.3#openapi-object).

### Шаг 3. Опишите входные данные и ответы

Для каждой операции последовательно перенесите сведения из своей таблицы в YAML.

1. **Назначение.** В `summary` запишите действие. В `description` можно указать роль и условие доступа из вашего сценария.
2. **Параметры.** Если в пути есть `{requestId}`, добавьте параметр с таким же именем, `in: path`, `required: true` и типом в `schema`. Фильтры и другие параметры после знака `?` описывайте с `in: query`, если они есть в вашей операции.
3. **Тело запроса.** Для операции, принимающей JSON, добавьте `requestBody` и тип содержимого `application/json`. В схеме укажите свойства, их типы и список обязательных полей. Добавьте пример допустимых данных.
4. **Ответы.** Под `responses` запишите код успешного ответа и коды ошибок из задания № 6. Для каждого укажите `description`. Если операция возвращает JSON, опишите его в `content` и приведите пример хотя бы для одного успешного ответа и одной ошибки.
5. **Повторяющиеся структуры.** Если создание и чтение возвращают заявку одинаковой структуры, опишите её один раз в `components.schemas`. Подключите эту схему к обоим ответам через `$ref`.

Проверьте, что имена, типы полей и условия ошибок совпадают с исходным описанием API. [Параметры OpenAPI](https://spec.openapis.org/oas/v3.0.3#parameter-object) · [Тело запроса](https://spec.openapis.org/oas/v3.0.3#request-body-object) · [Ответы](https://spec.openapis.org/oas/v3.0.3#responses-object).

### Шаг 4. Проверьте файл в Swagger Editor

1. Откройте Swagger Editor и вставьте YAML в область редактирования. Для внешнего редактора используйте учебные или обезличенные примеры.
2. Проверьте сообщения об ошибках и исправьте их. Начните с отступов, путей, объявлений параметров и ссылок `$ref`.
3. Откройте отображение каждой операции. Убедитесь, что видны нужные параметры, тело запроса и ответы. Сверьте пример JSON с указанными типами и обязательными полями.
4. Сохраните проверенный `openapi.yaml` и запишите, каким инструментом проверили файл.

Для задания достаточно проверки документа и разбора обмена по примерам. [Swagger Editor](https://editor.swagger.io/) · [Документация Swagger Editor](https://swagger.io/docs/open-source-tools/swagger-editor/).

### Шаг 5. Свяжите операции с действиями в интерфейсе

Составьте небольшую таблицу для одного пользовательского сценария. В первой колонке укажите действие, которое видно пользователю. Во второй — HTTP-метод, путь и данные запроса. В третьей — код и важные поля ответа. В четвёртой — что интерфейс показывает или делает дальше.

1. Покажите успешное создание. Отметьте, какой идентификатор интерфейс берёт из ответа и куда подставляет его в следующем запросе.
2. Покажите чтение результата. В кейсе «Север» по `Location` можно открыть созданную бронь, а повторное чтение заявки показывает обновлённый статус.
3. Покажите одну ошибку. Например, если сервер указал, что обязательное поле пропущено, опишите, у какого поля появится сообщение и как пользователь продолжит работу.

Рядом с таблицей запишите результат проверки YAML и кратко укажите, какой ответ ведёт к следующему шагу в интерфейсе, а какой оставляет пользователя на текущем шаге. Сохраните этот файл для проверки CI в задании № 13 и тестирования API в задании № 14.

## Подсказки по ключевым частям

- **Параметр пути и поле в JSON.** `requestId` в пути указывает, какую заявку запросить. Поля `equipmentId` и `requestedFor` в теле передают данные для создания новой заявки.
- **Обязательное тело и обязательные поля.** `requestBody.required: true` означает, что операция требует тело запроса. Список `required` внутри схемы задаёт обязательные поля в этом теле.
- **Схема и пример.** Схема описывает допустимую структуру данных. Пример показывает конкретный запрос или ответ, который ей соответствует.
- **Код ответа и состояние заявки.** Код `201` говорит, что ресурс создан. Поле `status: PENDING` показывает, что по самой заявке ещё предстоит принять решение.

### Пример OpenAPI для сервиса выдачи оборудования

В примере сохранены пути, поля и идентификаторы из задания № 6. Замените их значениями из своего сценария.

```yaml
openapi: 3.0.3
info:
  title: API выдачи оборудования
  version: '1.0.0'
paths:
  /equipment-requests:
    post:
      summary: Создать заявку на оборудование
      description: Сотрудник создаёт заявку от своего имени.
      operationId: createEquipmentRequest
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/EquipmentRequestInput'
            example:
              equipmentId: EQ-17
              requestedFor: '2026-11-16'
      responses:
        '201':
          description: Заявка создана
          headers:
            Location:
              description: Путь к созданной заявке
              schema:
                type: string
              example: /equipment-requests/REQ-101
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/EquipmentRequest'
        '400':
          description: Некорректные входные данные
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/ApiError'
              example:
                code: REQUIRED_FIELD_MISSING
                message: Укажите дату выдачи
                field: requestedFor
  /equipment-requests/{requestId}:
    get:
      summary: Получить заявку на оборудование
      description: Автор получает сведения о своей заявке.
      operationId: getEquipmentRequest
      parameters:
        - name: requestId
          in: path
          required: true
          description: Идентификатор заявки
          schema:
            type: string
          example: REQ-101
      responses:
        '200':
          description: Сведения о заявке
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/EquipmentRequest'
        '404':
          description: Заявка не найдена
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/ApiError'
              example:
                code: REQUEST_NOT_FOUND
                message: Заявка не найдена
components:
  schemas:
    EquipmentRequestInput:
      type: object
      required: [equipmentId, requestedFor]
      properties:
        equipmentId:
          type: string
        requestedFor:
          type: string
          format: date
    EquipmentRequest:
      type: object
      required: [requestId, equipmentId, requestedFor, status]
      properties:
        requestId:
          type: string
        equipmentId:
          type: string
        requestedFor:
          type: string
          format: date
        status:
          type: string
          description: Текущее состояние заявки
      example:
        requestId: REQ-101
        equipmentId: EQ-17
        requestedFor: '2026-11-16'
        status: PENDING
    ApiError:
      type: object
      required: [code, message]
      properties:
        code:
          type: string
        message:
          type: string
        field:
          type: string
```

### Пример таблицы взаимодействия

| Действие пользователя | Запрос | Ответ бэкенда | Что делает интерфейс |
| --- | --- | --- | --- |
| Отправляет заполненную заявку. | `POST /equipment-requests` с `equipmentId` и `requestedFor`. | `201`, `requestId: REQ-101`, `status: PENDING`. | Показывает номер заявки и статус «На рассмотрении». Сохраняет идентификатор для открытия карточки. |
| Открывает карточку созданной заявки. | `GET /equipment-requests/REQ-101`. | `200` и актуальные сведения о заявке. | Показывает данные и переводит значение `status` в понятную пользователю подпись. |
| Отправляет заявку без даты выдачи. | `POST /equipment-requests` с `equipmentId`, поле `requestedFor` пропущено. | `400`, `code: REQUIRED_FIELD_MISSING`, `field: requestedFor`. | Оставляет пользователя на форме, сохраняет введённые данные и показывает сообщение рядом с полем даты. |
