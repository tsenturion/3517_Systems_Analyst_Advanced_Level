Практика для самостоятельного закрепления навыков. Сдача по желанию.

## Цель

Подготовить и выполнить три проверки одной операции API. Сравнить ожидаемые и фактические ответы, проверить состояние данных после запроса и показать, какое требование покрывает каждая проверка.

### Шаг 2. Подготовьте три проверки до запуска

Для учебного стенда все заявки относятся к аудитории `A-203` и дате 6 октября 2026 года, время UTC+5. Уже есть подтверждённая бронь `BKG-900` с 10:00 до 11:00. Следующие заявки изначально имеют статус `PENDING` («На рассмотрении»).

| ID проверки | Тип | Заявка | Запрошенный интервал |
| --- | --- | --- | --- |
| API-01 | Обычный успешный сценарий | `REQ-101` | 13:00–14:00 |
| API-02 | Отказ по бизнес-правилу | `REQ-102` | 10:30–11:30 |
| API-03 | Пограничный сценарий | `REQ-103` | 11:00–12:00 |

Для каждой проверки запишите идентификатор критерия из задания № 12 и, если есть, связанного требования. Укажите исходные данные, HTTP-метод и путь, ожидаемый HTTP-статус, важные поля ответа и ожидаемое состояние заявки после запроса. Для варианта «Север» сопоставьте свой контракт с возможностями стенда ниже.

| Операция стенда | Что возвращает |
| --- | --- |
| `GET /booking-requests/{requestId}` | `200 OK`, данные заявки, поле `status` и поле `bookingId`. У заявки на рассмотрении `status: PENDING` и `bookingId: null`, у подтверждённой — `status: CONFIRMED` и идентификатор брони. |
| `POST /booking-requests/{requestId}/bookings` без тела | При создании брони — `201 Created`, данные брони и заголовок `Location` с путём к ней. При пересечении интервалов — `409 Conflict` и `{"code":"BOOKING_CONFLICT"}`. |
| `GET /bookings/{bookingId}` | `200 OK`, данные брони с полями `bookingId`, `requestId`, `roomId`, `startsAt` и `endsAt`. |

Например, для `API-01` ожидайте `201`, заголовок `Location: /bookings/BKG-101` и бронь для `REQ-101` на 13:00–14:00. Затем ожидайте у заявки статус `CONFIRMED` и ссылку на ту же бронь. По аналогии запишите ожидания для пересечения и смежных интервалов. [Код 201 и заголовок Location в HTTP](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.2) · [Код 409 в HTTP](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.10).

### Шаг 4. Выполните три проверки и сохраните фактические ответы

1. **Обычный сценарий.** Первым `GET` убедитесь, что `REQ-101` на рассмотрении и `bookingId` равен `null`. Выполните `POST`, запишите его статус, `Location` и значимые поля тела. Повторите `GET` заявки. Откройте бронь по пути из `Location` и сверьте идентификатор заявки, аудиторию и интервал.

```powershell
curl.exe -i http://127.0.0.1:8765/booking-requests/REQ-101
curl.exe -i -X POST http://127.0.0.1:8765/booking-requests/REQ-101/bookings
curl.exe -i http://127.0.0.1:8765/booking-requests/REQ-101
curl.exe -i http://127.0.0.1:8765/bookings/BKG-101
```

2. **Отказ при пересечении.** Прочитайте заявку `REQ-102`, отправьте `POST` и снова прочитайте заявку. Сверьте HTTP-статус, код ошибки в JSON, статус заявки и поле `bookingId` после попытки подтверждения.

```powershell
curl.exe -i http://127.0.0.1:8765/booking-requests/REQ-102
curl.exe -i -X POST http://127.0.0.1:8765/booking-requests/REQ-102/bookings
curl.exe -i http://127.0.0.1:8765/booking-requests/REQ-102
```

3. **Граница интервала.** Сравните конец `BKG-900` с началом заявки `REQ-103`. Затем повторите последовательность из обычного сценария для `REQ-103`. При создании брони прочитайте её по пути из `Location` и проверьте, что она начинается в 11:00. Запишите, как этот результат связан с правилом о смежных интервалах.
4. Для каждого случая сравните фактический результат с ожиданием из шага 2. Если хотите повторить весь прогон, остановите стенд клавишами `Ctrl+C` в первом терминале и запустите заново. При новом запуске восстанавливаются исходные данные. После завершения работы остановите стенд.

## Подсказки по ключевым частям

- **Связь с требованием.** У одного требования может быть несколько проверок. Для `FR-03` успешный случай показывает, что свободный интервал можно подтвердить, отказ проверяет запрет пересечения, а пограничный случай проверяет допустимость смежных интервалов.
- **Статус ответа и результат проверки.** Ожидаемый `409` означает, что проверка отказа прошла, если совпали также код ошибки и состояние данных. Например, стенд возвращает `409` с кодом `REQUEST_ALREADY_CONFIRMED` при повторном подтверждении уже обработанной заявки. Это другой исход, чем `BOOKING_CONFLICT`.
- **Ответ и состояние данных.** После `201` проверьте, что заявка действительно подтверждена и бронь доступна по `Location`. После отказа повторный `GET` покажет, сохранился ли исходный статус заявки и осталась ли она без брони.
- **Условия запуска.** Если терминал сообщает, что соединение не установлено, проверьте, работает ли стенд и совпадает ли порт. Если сервер ответил `404`, проверьте метод, путь и идентификатор в запросе.

- [ ] Указаны операция, тестовая среда и требование или критерий приёмки.

- [ ] Ожидаемые HTTP-статусы, поля ответов и состояние данных записаны до запуска.
- [ ] После запросов подтверждения отдельно проверено состояние заявок. Для успеха проверены данные созданной брони.
- [ ] Фактические ответы зафиксированы, у каждой проверки есть итог, а для расхождения записаны шаги воспроизведения.
- [ ] В выводе указано, какие условия выбранного требования проверены.

## Советы по улучшению работы

- В запросах по времени сохраняйте дату и часовой пояс. Сравнивайте полные значения времени, чтобы одинаковые часы на разных датах не выглядели смежными.
- Добавьте в отчёт одно короткое свидетельство на каждый результат. Для пересечения достаточно строки HTTP-статуса, JSON с кодом ошибки и полей `status` и `bookingId` из повторного чтения заявки.
- При повторном прогоне начинайте с одинакового состояния. Так можно отличить дефект от результата, который изменился из-за предыдущих запросов.
