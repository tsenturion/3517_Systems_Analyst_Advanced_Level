# Практическое задание «Декомпозиция задач и критерии приёмки»

**Тема курса** — 7.1 «Сложности декомпозиции задач, критерии готовности и приёмка».

Практика для самостоятельного закрепления навыков. Сдача по желанию.

## Цель

Разбить один пользовательский сценарий на 3–5 задач с конкретными результатами и зависимостями. Для одной задачи определить, что нужно перед началом работы и по каким признакам можно принять результат.

## Задание

### Шаг 1. Опишите границы одного сценария

Откройте сценарий итогового проекта из задания № 4 и контракт из задания № 7. Выберите операцию проекта, которая меняет состояние. В 3–5 предложениях укажите, кто выполняет действие, с какого состояния оно начинается, какой результат нужен и в каком случае результат будет другим. Укажите метод и путь операции, источник бизнес-правила и принятые допущения. [Задание № 4 «Проектирование информационной модели»](./04-Практическое-задание-Информационная-модель.md) · [Задание № 7 «Контракт OpenAPI и взаимодействие фронтенда с бэкендом»](./07-Практическое-задание-OpenAPI.md).

**Маршрут для кейса «Север».** Администратор открывает разовую заявку на аудиторию со статусом «На рассмотрении» и выбирает «Подтвердить». Из контракта возьмите `POST /booking-requests/{requestId}/bookings`. При успехе появляется одна бронь на ту же аудиторию и интервал, а заявка получает статус «Подтверждена». Если интервал пересекается с подтверждённой бронью этой же аудитории, система сообщает о конфликте. Если существующая бронь заканчивается ровно в момент начала запрошенного интервала, подтверждение допустимо. [Требование FR-03 в задании № 3](./03-2.12-Практическое-задание-Управление-изменениями-и-трассировка.md).

Для базового упражнения считайте, что в выбранный день нет служебных закрытий и заявки подтверждаются по очереди. При конфликте заявка остаётся на рассмотрении, новая бронь не создаётся.

### Шаг 2. Разбейте сценарий на 3–5 задач

1. Пройдите основной ход и исключение от действия пользователя до результата. Для каждого выпишите, что потребуется определить, изменить или проверить.
2. Объедините действия с одним общим результатом. Например, если для операции нужно согласовать условия успеха и ошибки, результатом задачи может стать один контракт с обоими исходами.
3. Дайте каждой задаче идентификатор и название с действием. В отдельной колонке укажите результат, который можно показать или проверить. Вместо «Сделать API» укажите, какую операцию можно вызвать, что она возвращает и какое изменение данных даёт.
4. Проверьте границы. Все задачи вместе должны давать описанный пользовательский результат, включая исключение. Если две задачи обещают один и тот же результат, уточните, за что отвечает каждая, или объедините их.

| --- | --- | --- | --- |
| T1 | … | … | … |
| T2 | … | … | … |
| T3 | … | … | … |

### Шаг 3. Укажите зависимости и условия старта

1. Для каждой строки спросите, какой результат другой задачи понадобится. Если зависимость есть, укажите её идентификатор и нужный результат. Например, для показа ошибки интерфейсу нужен согласованный формат ответа API. Если зависимостей внутри этого списка нет, поставьте прочерк.
2. Запишите предполагаемый порядок выполнения. Отдельно отметьте, какие задачи можно начать параллельно. Например, после согласования контракта экран можно подготовить на примерах ответов, пока реализуется API. Для совместной проверки понадобятся оба результата.
3. Выберите задачу, которая реализует поведение выбранной операции. Запишите два условия, которые нужно выполнить перед её началом. Это могут быть согласованное бизнес-правило, определённый контракт или подготовленные примеры входных данных. Укажите, что делать, если одно из условий ещё не выполнено.

### Шаг 4. Напишите критерии приёмки для выбранной задачи

Сформулируйте три критерия. Первый пусть описывает обычный успешный случай, второй — ошибку или отказ, третий — пограничный случай, важный для правила. Для «Севера» границу удобно проверить на двух интервалах, у которых совпадают конец первого и начало второго.

| ID | Дано — исходное состояние и данные | Когда — одно действие | Тогда — наблюдаемый результат |
| --- | --- | --- | --- |
| AC1 | … | … | … |
| AC2 | … | … | … |
| AC3 | … | … | … |

В колонке «Дано» укажите значения, по которым можно отличить случаи, например два интервала времени и статус заявки. В колонке «Когда» запишите действие пользователя или вызов операции API. В колонке «Тогда» укажите, что можно увидеть или проверить — ответ API, состояние записи при повторном чтении или сообщение на экране. Для отказа отметьте, какие данные должны сохраниться. [Справочник Gherkin по формату Given, When, Then](https://cucumber.io/docs/gherkin/reference/#steps).

### Шаг 5. Проверьте формулировки на примерах и соберите результат

1. Для каждого критерия запишите, где будете проверять результат и что именно сравните. Например, после отказа повторно откройте заявку и сравните её статус с исходным. Для проверки создания брони заранее определите, где можно увидеть её идентификатор, аудиторию и интервал.
2. Если для проверки приходится угадывать данные, действие или ожидаемый ответ, уточните формулировку. Если не хватает самого правила, запишите конкретный вопрос к его владельцу и отметьте, какие задачи или критерии зависят от ответа. Для этой практики достаточно пройти шаги на бумаге.
3. Добавьте в итоговый проект Markdown-файл с границами сценария, ссылкой на операцию в контракте, таблицей задач с зависимостями, порядком работы, двумя условиями старта и тремя критериями приёмки. Рядом с каждым критерием добавьте способ проверки. По этим критериям подготовьте проверки API в задании № 14.

## Подсказки по ключевым частям

### Как связать задачи с результатами

Пример для другого сценария — слушатель записывается на курс, пока на нём есть свободные места.

| ID | Задача | Результат | От какой задачи зависит и почему |
| --- | --- | --- | --- |
| T1 | Описать контракт записи на курс | Согласованы входные данные и два исхода операции — запись создана или свободных мест нет. Для каждого исхода есть пример ответа. | — |
| T2 | Реализовать запись при наличии места | Операцию можно вызвать по контракту. При успехе она создаёт запись и возвращает её идентификатор. При отсутствии мест возвращает отказ. | T1 — нужны согласованные входные данные и ответы. |
| T3 | Показать результат записи в интерфейсе | После отправки формы слушатель видит подтверждение записи или сообщение об отсутствии мест. | T1 — нужны примеры ответов. Результат T2 понадобится для совместной проверки с API. |

В примере T2 и T3 можно начать после T1. Работу интерфейса можно проверить на примерах ответов, а совместную проверку провести после готовности обеих задач.

### Как различать условия старта, приёмку и готовность результата

- **Условие старта** помогает понять, можно ли брать задачу в работу. Для T2 уже согласован формат ответа при отсутствии мест и известно, как определяется число свободных мест.
- **Критерий приёмки** описывает поведение, которое должна дать конкретная задача. Для T2 при наличии ровно одного свободного места операция записи создаёт одну запись, возвращает её идентификатор, а число свободных мест становится равным нулю. Проверить это можно по ответу операции и повторному чтению данных.
- **Определение готовности (Definition of Done)** в Scrum описывает состояние инкремента, который соответствует общим требованиям к качеству продукта. Например, команда может включить в него успешное прохождение автоматических проверок. [Руководство по Scrum об определении готовности](https://scrumguides.org/scrum-guide.html#commitment-definition-of-done).

## Что проверить перед отправкой

- [ ] Выбран один сценарий. Указаны роль пользователя, исходное состояние, ожидаемый результат и исключение.
- [ ] Сценарий разбит на 3–5 задач. У каждой есть идентификатор, конкретный результат и объяснение зависимости или прочерк.
- [ ] Порядок выполнения согласуется с зависимостями. Если задачи можно начать параллельно, это отмечено.
- [ ] Для одной задачи записаны два условия старта и три критерия приёмки с исходными данными, действием и ожидаемым результатом.
- [ ] У каждого критерия есть способ проверки. Для отказа понятно, как проверить результат операции и состояние данных.
- [ ] Вопросы по правилам и учебные допущения отмечены там, где они влияют на задачи или приёмку.

## Советы по улучшению работы

- Проверьте формулировки «корректно», «быстро» и «успешно». Замените их значением, статусом, сообщением или другим наблюдаемым результатом.
- Если в одной задаче несколько результатов, проверьте, можно ли принять их независимо. Если да, выделите отдельные задачи и пересмотрите зависимости.
- Привяжите каждый критерий к правилу или требованию. Идентификаторы `AC1`, `AC2` и `AC3` помогут позже связать критерии с проверками API.
- Если берёте расширенный кейс «Север», отдельно рассмотрите служебное закрытие или два одновременных подтверждения. Зафиксируйте правило и обновите задачи и критерии, которых оно касается.

## Вопросы для рефлексии

1. Какой результат сценария определил границу между двумя вашими задачами?
2. Какую зависимость можно ослабить, если заранее согласовать контракт или пример ответа?
3. Какое условие старта предотвратит больше всего переделок для выбранной задачи?
4. Какой критерий оказалось труднее всего сделать проверяемым и каких сведений для этого не хватало?
5. Как изменятся задачи и критерии, если результат операции понадобится проверить при двух одновременных действиях пользователей?
